# Kyokushin NN — AI context

## Mission

Maintain a fast, trustworthy recruitment microsite for the Nizhny Novgorod Shinkyokushinkai federation. The owner-visible outcome is simple: a parent or student can understand the offer, find a suitable hall, see the relevant instructor and schedule, and contact the instructor directly.

## Canonical source surfaces

- `script.js` — instructors, halls, addresses, schedules and filtering data.
- `media.js` — gallery and photo-report registry.
- `trainer-photos.js` — source-bound trainer portraits and identity-safe fallbacks.
- `team.js` — trainer roster rendering.
- `finder.js` — shareable search/filter state.
- `photo.js` — gallery, albums and lightbox behavior.
- `styles.css`, `cards.css`, `media-viewer.css`, `art-direction-v2.css`, `experience.css` — visual system.
- `scripts/build-static.mjs` — canonical self-contained production bundle.
- `scripts/verify.mjs` and focused verifier scripts — deterministic regression gates.
- `vercel.json` — production build/output contract.
- `.github/workflows/kyokushin-nn-ci.yml` — release verification and deployment pipeline.

## Non-negotiable invariants

- Keep exactly the verified recruitment data unless a new source explicitly changes it: 18 halls and 11 instructors.
- Never invent a schedule, rank, title, identity or personal photo.
- Personal trainer images require an explicit source-bound identity match; otherwise use the neutral fallback.
- Preserve direct `tel:` contact and map access for every applicable hall.
- Production must serve the self-contained HTML generated by `npm run build` directly.
- Never deploy a browser-side binary/bootstrap loader, `p*.bin` payload reconstruction, runtime gzip assembly or similar client-side packaging.
- Do not make GitHub Raw/CDN fallback loaders part of the production success path.
- A Vercel deployment being `READY` is not sufficient evidence. The public production URL must pass the production smoke contract.
- Do not hide production failures behind a fallback that reports success while the actual recruitment UI is unavailable.

## Working loop

For a bug or regression:

`reproduce/fingerprint -> establish root cause -> smallest causal fix -> focused regression check -> npm run check -> verify affected real surface`

For release/deployment work:

`npm run check -> release contract -> deploy exact verified source -> public production smoke`

Do not add a third preparatory implementation pass without new decisive runtime/visual evidence.

## Verification commands

```bash
npm run check
npm run verify:release
npm run smoke:production
```

`smoke:production` is a live check against `https://kyokushin-nn.vercel.app/` and is expected to fail closed when production is stale, bootstrapped through binary chunks, missing the required UI markers, or unavailable.

## Definition of done

A change is done only when the relevant source checks pass and the requested terminal surface is proven. For production work that means the public domain returns the real self-contained site directly and the live smoke passes; CI success alone is not a substitute.
